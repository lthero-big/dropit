dropit is a single-process application: one Node process serves the frontend static files, the HTTP API and WebSocket, and stores data in a SQLite database and a file directory under `DATA_DIR` (`/data` in the image).

## Recommended topology

```
Browser / CLI ──HTTPS──▶ nginx (TLS termination, 443) ──HTTP──▶ dropit container 127.0.0.1:8787 ──▶ volume dropit-data:/data
```

## Docker Compose

```yaml
services:
  dropit:
    image: lthero1/dropit:latest     # or build: . to build from source
    container_name: dropit
    restart: unless-stopped
    ports:
      - "127.0.0.1:8787:8787"
    env_file: .env                   # optional: OAuth credentials, ADMIN_EMAIL / ADMIN_PASSWORD, etc.
    environment:
      NODE_ENV: production
      APP_ORIGIN: https://dropit.example.com
      TRUST_PROXY: loopback
    volumes:
      - dropit-data:/data
volumes:
  dropit-data:
```

If nginx runs on the host and requests enter the container through the Docker bridge gateway, `TRUST_PROXY` must include that gateway address (for example, after pinning the network to a fixed subnet, use `loopback,10.87.87.1`).

First deployment: `docker compose up -d` → `docker logs dropit 2>&1 | grep 'setup code'` for `dropit setup code: XXXX-XXXX` → open `/setup` in the browser and create the admin. Alternatively set both `ADMIN_EMAIL` / `ADMIN_PASSWORD` in `.env` to create the admin on an empty database at startup. Finish initialisation of a public instance right after it starts.

`APP_ORIGIN` can also be left out of compose and set after deployment in “Admin → Site address” (the admin setting wins over env). If the proxy is not in `TRUST_PROXY` and no site address is set, dropit cannot see the original https, so generated OAuth callbacks will be http — set a site address or `TRUST_PROXY`. The `dropit APP_ORIGIN:` startup log line shows the effective value.

The image ships with a `HEALTHCHECK` (requests `/healthz`) and runs as the non-root user `node`.

## nginx

```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 443 ssl;
    server_name dropit.example.com;
    # ssl_certificate ... / ssl_certificate_key ...

    client_max_body_size 30m;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_request_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

- `client_max_body_size` must be larger than the upload chunk size `UPLOAD_CHUNK_BYTES` (8 MiB by default, hard cap 24 MiB); 30m covers the cap.
- A long `proxy_read_timeout` keeps the proxy from closing WebSockets too early; clients also reconnect automatically.

## HTTP deployment on an internal network

Without TLS the default image (`NODE_ENV=production`) works as is. `APP_ORIGIN` can be left unset (the access address is used) or set to the address you use; cookies are then not Secure, and the log and admin panel warn that the site is HTTP:

```bash
docker run -d --name dropit \
  -p 192.168.1.10:8787:8787 \
  -e APP_ORIGIN=http://192.168.1.10:8787 \
  -e GITHUB_CLIENT_ID -e GITHUB_CLIENT_SECRET \
  -v dropit-data:/data lthero1/dropit:latest
```

Bind only to the internal address — do not publish on `0.0.0.0` and do not set up port forwarding. Register this origin as the OAuth callback.

## Upgrading

Database migrations run automatically and atomically at startup, based on `user_version`. Back up before upgrading. Upgrading to schema 16 (the room code is the link; old long room links removed) first copies the database to `<database file>.pre-v<old version>-<time>.bak` in the same directory, then migrates.

| Install method | Upgrade command |
| --- | --- |
| Docker image (`image: lthero1/dropit:latest`) | `docker compose pull && docker compose up -d` |
| Docker Compose built from source | `./scripts/update.sh --docker` |
| Source install (pnpm + systemd / pm2) | `./scripts/update.sh` |

The bundled `docker-compose.yml` contains both `image: lthero1/dropit:latest` and `build:`: `docker compose pull` pulls the Docker Hub image, while `docker compose up -d --build` builds from source and tags it with the same name. Pick one and don't mix them, otherwise the next `pull` will overwrite your local build with the Hub image.

### Version numbers

- Every build carries a version and short git hash: the image writes them via the build-args `DROPIT_VERSION` / `DROPIT_COMMIT` / `DROPIT_BUILD_DATE` into environment variables and OCI labels (`org.opencontainers.image.version` / `.revision` / `.created`); source installs get `apps/server/build-info.json` generated by `pnpm build`.
- `GET /api/version` returns `{"version","commit","buildDate","install"}`, where `install` is `docker` (Hub image), `docker-build` (compose local build) or `source`.
- Include the commit when building the image locally: `DROPIT_COMMIT=$(git rev-parse --short HEAD) docker compose up -d --build` (`scripts/update.sh --docker` sets it automatically).
- `docker image inspect lthero1/dropit:latest --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}'` shows the commit an image was built from.

### Detecting new versions

By default the server checks every 12 hours (cached in `DATA_DIR/update-check.json`, so restarts don't trigger extra requests):

- Docker image: reads the digest of Docker Hub `lthero1/dropit:latest` and the commit / version tags sharing that digest, then uses GitHub compare to decide whether it is newer than the current one.
- Source install / local build: uses GitHub compare between the current commit and upstream `main` and shows how many commits behind you are.
- Both also consult GitHub Releases: a newer semver release is reported as well.

Admins can see the current version, last check time, latest version and the upgrade command for their install method under “Admin → Updates”, and can “Check now”; when a new version is available a notice appears at the top of the admin and settings pages. Checks are anonymous GET requests and upload no instance information. If offline or blocked by a firewall, only a single warning is logged and “Check failed” is shown; usage is unaffected and it retries next cycle. For fully offline deployments set `UPDATE_CHECK=false`; see [Configuration](../../config/configuration/#update-checks) for the related variables.

### Automatic updates (optional)

Docker image deployments can enable the `watchtower` service in the compose file (not started by default):

```bash
docker compose --profile autoupdate up -d
```

It uses the still-maintained `nickfedor/watchtower` (the original `containrrr/watchtower` is archived and doesn't support Docker 29+) with `--label-enable --cleanup --interval 43200`: it only updates containers labelled `com.centurylinklabs.watchtower.enable=true` (i.e. dropit), pulls `latest` every 12 hours, recreates the container once the new image is ready and cleans up old images. It needs `/var/run/docker.sock` mounted, which is equivalent to root on the host — evaluate that yourself; if you'd rather not, stick with the manual commands.

If your own compose file already runs a watchtower, just add the same label to dropit; there's no need to run a second one.

### Source install script

`scripts/update.sh` runs `git pull --ff-only`, `pnpm install --frozen-lockfile` and `pnpm build` in order, then restarts:

- If `DROPIT_RESTART_CMD` is set, it runs that (e.g. `DROPIT_RESTART_CMD="systemctl restart dropit"`);
- otherwise it runs `systemctl restart dropit` if `dropit.service` exists, or `pm2 restart dropit` if a pm2 app named `dropit` exists;
- if neither exists, it only builds and asks you to restart manually.

`--check` only reports how many commits behind upstream you are; `--docker` switches to `docker compose up -d --build`. The script refuses to run if tracked files have local modifications; when already up to date it skips the build (`FORCE=1` forces a rebuild).

## Backup and restore

- Use the SQLite backup API (e.g. `sqlite3 dropit.sqlite ".backup backup.sqlite"`), or stop the service and copy the whole data directory.
- Don't just copy the `.sqlite` file while it is running; back up the database and the file directory together.
- Deleting the data volume also deletes the content, runtime limit overrides and audit log.

## Limitations

- Only a single instance is supported: rate limits, broadcasts, online counts and upload concurrency counters live in process memory, so never let multiple instances share the same data directory.
